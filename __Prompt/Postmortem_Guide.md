# Blameless Postmortem 가이드

> **목적**: 인시던트를 비난 없이 학습으로 전환하고, 재발 방지 조치를 리뷰 파이프라인에 반영합니다.
> **참조**: Review_Pipeline_Guide.md Section 12.6 (인시던트 발생 시), TO-BE.md P1-4

---

## 1. Blameless 원칙

1. **사람이 아니라 시스템을 고친다**: "누가 실수했나"가 아니라 "왜 시스템이 그 실수를 허용했나"를 묻습니다.
2. **처벌 없음 보장**: 처벌이 없어야 정직한 타임라인이 나옵니다. 숨긴 사실이 있는 포스트모텀은 가치가 없습니다.
3. **행운도 기록한다**: "운이 좋아서 막은 것"은 다음에는 사고가 됩니다. near-miss도 학습 대상입니다.

---

## 2. 수행 기준 (언제 하는가)

| 조건 | 포스트모텀 |
|------|-----------|
| 사용자 영향 발생 (다운타임, 오동작, 데이터 이슈) | **필수** |
| 롤백 수행 (Review_Pipeline_Guide.md Section 12.5 기준 발동) | **필수** |
| SLO 위반 또는 온콜 페이지 발생 | **필수** |
| 아차 사고 (near-miss, 배포 직전 발견 등) | 권장 |

- **시점**: 해결 후 **24~72시간 이내** (기억이 선명하고, 급한 불은 꺼진 시점)
- **작성자**: 인시던트 오너가 초안 작성 → 관련자 전원 리뷰 → 팀 공유

---

## 3. 프로세스

```
[인시던트 발생]
  ↓
[감지] ← 모니터링 알림 / 사용자 제보
  ↓
[에스컬레이션] → 인시던트 오너 지정 (Review_Pipeline_Guide.md Section 7)
  ↓
[완화] → 롤백, Feature Flag OFF, 우회 (원인 분석보다 영향 차단 우선)
  ↓
[해결] → 근본 원인 수정
  ↓
[포스트모텀] ← 24~72시간 내 수행
  ↓
[프로세스 개선] → Action Item 실행, 체크리스트/가이드 반영
```

---

## 4. 템플릿 (복사해서 사용)

```markdown
# Postmortem: [제목] (YYYY-MM-DD)

## 요약
| 항목 | 내용 |
|------|------|
| 발생 시각 | YYYY-MM-DD HH:MM |
| 감지 시각 | YYYY-MM-DD HH:MM (감지까지 N분) |
| 해결 시각 | YYYY-MM-DD HH:MM (총 지속 N시간) |
| 영향 범위 | 영향받은 사용자 수 / 기능 / 데이터 |
| 심각도 | SEV1 (전면 장애) / SEV2 (부분 장애) / SEV3 (경미) |
| 인시던트 오너 | @name |
| 관련 PR/배포 | #PR번호, 배포 ID |

## 타임라인
| 시각 | 이벤트 |
|------|--------|
| HH:MM | 변경 배포됨 (PR #N) |
| HH:MM | 이상 감지 (알림/제보 경로 명시) |
| HH:MM | 에스컬레이션, 인시던트 오너 지정 |
| HH:MM | 완화 조치 (롤백/플래그 OFF) |
| HH:MM | 근본 원인 수정 배포 |
| HH:MM | 정상화 확인 |

## 근본 원인 (5 Whys)
- **Why 1**: 왜 장애가 발생했는가? →
- **Why 2**: 왜 그것이 가능했는가? →
- **Why 3**: 왜 사전에 잡히지 않았는가? →
- **Why 4**: 왜 프로세스가 그것을 허용했는가? →
- **Why 5**: 왜 시스템이 그렇게 설계되었는가? →

## 교훈
- **잘된 점**: (빠른 감지, 원활한 에스컬레이션 등)
- **개선할 점**: (감지 지연, 롤백 절차 미비 등)
- **운이 좋았던 점**: (트래픽이 적은 시간대였음 등 — 다음엔 행운이 없다고 가정)

## 리뷰 파이프라인 점검 (필수 질문)
- [ ] 이 결함은 코드 리뷰에서 잡을 수 있었는가?
- [ ] 잡을 수 있었다면: 어떤 체크리스트 항목/분류 기준이 있었어야 하는가?
- [ ] 분류(Risk/Tier)는 적절했는가? (과소 분류로 얕은 리뷰를 받지 않았는가)

## Action Items
| # | 조치 | 유형 | 담당 | 기한 | 추적 |
|---|------|------|------|------|------|
| 1 | | 재발 방지 / 감지 개선 / 프로세스 개선 | @name | YYYY-MM-DD | 티켓 링크 |
```

## 5. 리뷰 파이프라인 피드백 루프

포스트모텀의 핵심 산출물은 **파이프라인 개선**입니다:

1. "리뷰에서 잡을 수 있었나?" → **YES**인 경우:
   - 해당 유형의 체크리스트 항목 추가 (`Review_Pipeline_Guide.md` Section 4)
   - 자동 분류 기준 보강 (Section 9 — 경로/키워드 패턴 추가)
   - 분류가 과소했다면 Tier 결정 로직 재검토 (Section 3.1)
2. 가이드 변경은 PR로 생성하고 변경 이력에 기록 → 다음 리뷰부터 즉시 적용
3. 월간 메트릭 사이클(Section 13.4)에서 Action Item 완료 여부 추적

## 6. 안티패턴

| 안티패턴 | 문제 |
|----------|------|
| 이름 지목, 비난성 표현 | 다음 인시던트부터 정보가 숨겨짐 |
| "더 조심하자"류 결론 | 사람 의존 조치는 재발 방지가 아님. 시스템/자동화 조치로 전환할 것 |
| Action Item 없는 포스트모텀 | 기록만 남고 개선 없음 |
| 90일 넘게 열린 Action Item | 사실상 하지 않겠다는 뜻. 기한 재조정 또는 명시적 폐기 결정 필요 |
| 심각도 축소 | SEV 낮추기 경쟁은 학습 기회 상실 |
